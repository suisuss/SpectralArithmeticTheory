## 1. The rotation calculus (starting point)

A formal language with one rewrite rule, one data structure, one constraint parameter:

```
observe(pair(a, b)) -> pair(b, observe(a))    if C(a, b)
observe(pair(a, b)) -> stuck                   if not C(a, b)
observe(ground)     -> ground
```

Compact notation:

```
rho<a, b>  |->  <b, rho a>
rho .      |->  .
```

In lambda calculus with Scott-encoded pairs:

```
rho := Y(lambda r. lambda t. t . (lambda a. lambda b. pair b (r a)))
```

Which decomposes in BCKW combinators as `rho = Y(lambda r. C(B pair r))` — the rotation rule is the flip of compositional self-reference.

The deep point of the lambda encoding: observation is self-elimination. The term `pair a b` receives the rotation function and applies it to its own components. The term participates in its own observation. The notation `rho<a,b> |-> <b, rho a>` hides this. The lambda encoding reveals it: observation is self-elimination composed with rearrangement, at a fixed point.

Properties proved in Lean:
- Termination (pairsUnderObserve strictly decreases)
- No symbol creation (constructor count invariant)
- Deterministic confluence (at most one redex)
- Reversibility (step is invertible)

Working examples: sorting, graph coloring (K3 needs 3 colors), subset sum verification, brute-force search, constraint density measurement.

Key finding from building examples: adjacency constraints (sorting, coloring) work natively in the per-step `C(a, b)` framework. Global constraints (subset sum) require either a global verifier or state accumulation — the "smuggled payload" architecture. The constraint's power determines which problems it can express natively vs which need structural augmentation.

## 2. Falsification: flat-list rotation = permutation CSP

**File:** `SpectralArithmetic/Rotation/CSPEquivalence.lean`

Defined `SequentialCSP` (pairwise adjacent checks on permutations) and built bidirectional mappings with constrained rotation.

**Results:**

- `forward_verification`: any CSP check maps to an equivalent rotation constraint check. Fully proved.
- `backward_faithful_aux`: any pairwise rotation constraint maps back to an equivalent CSP check. Fully proved.
- `pairwise_equivalence`: CSP satisfiability iff rotation contractibility. Forward proved, reverse deferred (Mathlib permutation plumbing).
- `triConstraint_not_pairwise`: graph coloring uses remainder-inspection (walks entire carried content), placing the rotation calculus at the RemainderCSP level = general non-binary CSP.

**Property analysis — every rotation property is "free":**

| Property | Rotation proof | CSP equivalent |
|----------|---------------|----------------|
| Termination | pairsUnderObserve decreases | Iterating a finite list terminates |
| Confluence | step is a partial function | Left-to-right eval is deterministic |
| Conservation | constructorCount invariant | Verification doesn't modify instance |
| Reversibility | unstep inverts step | Permutations are invertible |
| Observation trace | (observed, carried, passed) | (current, remaining, verdict) |
| Group structure | S_n arrangement space | Permutation CSP has S_n too |

**Verdict:** The flat-list rotation calculus is Permutation CSP in different notation. Its genuine contribution is presentational (uniform term language, syntactic visibility of the verification/search gap), not proof-theoretic.

## 3. Falsification: generator fixed-point = P != NP restated

**File:** `SpectralArithmetic/Rotation/GeneratorFixedPoint.lean`

Direction 3 from conception.md: any polynomial solver must contain a "compression scheme" (encode, decode, generate), and the encode-generate-decode cycle has only the trivial fixed point (brute force).

**Result:** The compression scheme is definitionally interconvertible with a plain solver.

```lean
theorem compression_scheme_iff_solver (P : SearchProblem) :
    (exists (S : CompressionScheme P), S.isCorrect) <->
    (exists (solve : P.Instance -> P.Witness),
      forall x, P.verify x (solve x) = true)
```

Both directions are one-liners. Forward: `solve := S.decode . S.generate`. Backward: `Code := Witness, encode := id, decode := id, generate := solve`.

**The recursive structure dissolves:** "encode requires generate requires encode" says "to build a solver you need to solve the problem." Tautological. True for all problems, easy and hard alike.

**Spanning tree counterexample:** Exponential witness space (up to n^(n-2) spanning trees), polynomial solver (Kruskal's). The "cycle" exists for spanning trees too, yet the solver is polynomial. The argument cannot distinguish easy from hard problems.

**Verdict:** Direction 3 is P != NP in compression-scheme notation. Not a proof strategy.

## 4. Discovery: tree arrangements escape CSP equivalence

**File:** `SpectralArithmetic/Rotation/TreeArrangement.lean`

The rotation rule works on arbitrary nested terms, not just flat lists. When applied to trees, the constraint fires at every nesting level — between grouped substructures, not just between atomic elements.

**Data representation:**
- Leaf: `pair (natToTerm n) ground` (via `labeledElement`)
- Tree node: `pair leftSubtree rightSubtree`
- NOT the list encoding

**Balanced partition constraint:** at each node where both children are compound subtrees, check `treeSum(left) == treeSum(right)`.

**Key results on {2, 3, 7, 8} (total = 20):**

```
tree (pair(2,8), pair(3,7)):  sums 10 vs 10  -> PASSES
tree (pair(2,3), pair(7,8)):  sums 5  vs 15  -> FAILS
tree (pair(2,7), pair(3,8)):  sums 9  vs 11  -> FAILS
flat [2,3,7,8]:               first elem is leaf -> VACUOUS (always passes)
flat [8,7,3,2]:               first elem is leaf -> VACUOUS (always passes)
```

**The structural difference:** The same constraint, acting on the same elements, produces trivial results on flat lists and non-trivial results on trees. The tree SHAPE is where the computational content lives. Flat-list permutation CSP cannot express balanced partition as a constrained arrangement problem.

**Multi-level balance:** `((1,8),(5,4)) | ((2,7),(3,6))` passes at ALL levels — 18 vs 18 at top, 9 vs 9 at each subtree. This is a hierarchical decomposition problem not expressible in flat CSP.

**Brute-force search on 4 elements:** 104/120 tree arrangements pass the balanced constraint. Most tree shapes have at least one leaf child, so the constraint is vacuously satisfied. Only the balanced binary tree shape engages the sum check.

## 5. Trees are fundamental to complexity

A flat list has one structural dimension: **order**. Given n elements, you choose a permutation. That's n! arrangements. The constraint checks adjacent pairs. The search space is the symmetric group S_n.

A tree has two structural dimensions: **shape** and **placement**. Given n elements, you first choose a binary tree shape (Catalan(n) options), then place elements at the leaves (n! options). The constraint checks at every internal node. The search space is the product of the Catalan space and the symmetric group.

These two dimensions **interact**. The tree shape determines which pairs of elements are compared by the constraint. In a flat list, element i is always compared with element i+1 — the adjacency structure is fixed (a path graph). In a tree, the constraint fires on pairs determined by the shape. Different groupings produce different constraint checks.

The tree shape is a **strategy for decomposing the problem**. Choosing a tree shape is choosing how to partition the elements into subproblems. Choosing the leaf placement is solving each subproblem. The two choices are coupled — a good partition depends on which elements are in each group.

This is exactly what divide-and-conquer algorithms do. Merge sort chooses a balanced partition and solves recursively. Quicksort chooses a pivot (unbalanced partition) and solves recursively. **The tree shape IS the algorithm. The leaf placement IS the solution.**

For flat lists, the search space is n! and its structure is simple — the symmetric group is well-understood. For trees, the search space is Catalan(n) x n!, but the structure is **hierarchical**. Hierarchical search spaces have a property flat ones don't: **subtree independence**.

If the constraint is local — if checking `pair(a, b)` depends only on properties of a and b, not on their position in the larger tree — then subtrees can be solved independently. Solve the left subtree, solve the right subtree, check the root constraint. The search factorizes.

For a balanced tree of depth d with n = 2^d leaves: instead of searching n! arrangements, you search 2 x (n/2)! at each level, for d levels. The tree structure reduces the effective search space by enabling factorization.

**This is why tree decomposition is powerful in constraint satisfaction.** Treewidth bounds the factor by which the search space can be decomposed. Low treewidth means the problem factorizes well. High treewidth means it doesn't.

The rotation rule adds something specific. The traversal is deterministic and left-first. When observe hits `pair(a, b)`, it always descends into `a` first, carrying `b`. The tree isn't just a decomposition — it's a traversal order. The rotation visits every node in a specific sequence determined by the tree shape.

In a flat list, the traversal order IS the arrangement. In a tree, the traversal order is determined by the tree shape, but the arrangement also includes the leaf placement. Two degrees of freedom: how to traverse (shape) and what you encounter (placement).

In a flat list, the constraint is applied sequentially — a chain. Each check depends on the previous. No parallelism, no independence. In a tree, the constraint is applied hierarchically. Subtree checks are independent. The constraint is a tree, not a chain.

**For tree arrangements, the verification structure matches the problem structure.** If the problem is inherently hierarchical (balanced partitioning, recursive decomposition, divide-and-conquer), then the tree arrangement expresses it natively. The flat list forces every hierarchical problem into a sequential encoding, destroying the factorization.

The deep question: **for NP-complete problems, does there exist a tree shape where the constraint factorizes?** If yes for all instances, the problem is in P (divide and conquer works). If no for some instances, those instances are the hard ones. The hardness of an NP problem, in this framing, is the degree to which its constraint resists hierarchical decomposition — the degree to which no tree shape makes the subtrees independent.

## 6. Asymmetric information flow

**File:** `SpectralArithmetic/Rotation/TreeFlow.lean`

`verifyTree` processes both children independently — no information flows between subtrees. But the rotation rule's sequential traversal creates asymmetry: left is processed before right.

Implemented `verifyTreeCtx`: a context-aware verifier where left sees (right + outer context) but right sees (outer context only, left consumed).

**Result on {1, 2, 3, 4} with budget constraint:**

```
Total disagreements:           18 arrangements
Symmetric-only (pass sym, fail asym): 16
Asymmetric-only (fail sym, pass asym): 2
```

With tight budget constraint: **42 disagreements**. The tighter the constraint, the more the traversal order matters.

**Interpretation:**
- 16 cases where context makes things HARDER (left sees more total, making budget fraction harder to satisfy)
- 2 cases where context makes things EASIER (left can "justify" itself by seeing what's coming in the right subtree)
- The asymmetry is genuine: same constraint, same tree, different verdicts depending on traversal model

This has no flat-CSP or symmetric tree-CSP equivalent. The traversal order is computationally significant.

## 7. Constraint factorization

**File:** `SpectralArithmetic/Rotation/Factorization.lean`

Formalized the key concepts:

**Subtree independence:** A constraint is subtree-independent if its verdict at a node depends only on the immediate children, not on wider context. `verifyTree` and `verifyTreeCtx` agree iff the constraint is subtree-independent.

**Search factorization:** Valid subtrees compose into valid whole trees. Even subtree-independent constraints may not factorize as search — the partition of elements couples the subproblems.

**`verifyTree_pair` theorem:** Verified that `verifyTree C (pair a (pair b1 b2))` decomposes into root check AND both subtree checks.

**Factorizable partitions (6 elements {1..6}):**
- Sorted-leaves constraint: 5/5 partitions factorize (any split of sorted data works)
- Balanced constraint: 5/5 partitions factorize (constraint is local, even though search is hard)

**Root pass rate (4 elements {1..4}):**
- Sorted: `[(2,2), (1,1), (2,2)]` — 100% pass rate at every split point
- Balanced: `[(2,2), (0,1), (2,2)]` — the 2+2 split has **0% pass rate**

The middle `(0,1)` is the fingerprint of NP-hardness: for the equal-size split, no combination of subtree arrangements passes the root check. The partition IS the hard part — you can't solve it locally.

## 8. Corrections and tightening

Three claims from the analysis that need correction:

1. **"P = problems where decisions form a tree of polynomial depth with independent subtrees"** is too strong. P includes problems with high treewidth solved by non-tree methods (LP relaxations, spectral methods). Low treewidth -> P, but P does not imply low treewidth.

2. **NP-complete problems "resist catamorphism"** is instance-specific, not problem-level. Bounded-treewidth SAT is polynomial. The NP-completeness is about worst-case instances, not all instances.

3. **"Minimum tree depth capturing decision structure"** is circuit depth (parallel complexity / NC), not sequential complexity (P). P allows polynomial-depth sequential trees. NC requires polylogarithmic-depth parallel trees.

## 9. What's genuinely new

Three things the tree rotation framework provides that standard frameworks don't combine:

**1. The decomposition is the search object.** In standard treewidth analysis, you're given a constraint graph and analyze its treewidth. In tree rotation, the tree shape IS the arrangement — you search for a decomposition that satisfies constraints. The search space is (tree shapes x leaf placements). "Designing an algorithm" and "finding a satisfying arrangement" become the same activity.

**2. The constraint is level-uniform.** The same constraint C fires at every tree level. It doesn't know what depth it's at. The difficulty at level k comes from the SIZE of the subproblem, not from a different constraint. This creates a clean recursion: `difficulty(n) = difficulty_of_split(n) + 2 * difficulty(n/2)`.

**3. The traversal order creates asymmetric information flow.** The rotation rule's left-first descent means information flows differently through the tree. Left subtree constraints see the right subtree as context; right subtree constraints don't see left. This creates 18 disagreements on 4 elements between symmetric and asymmetric verification — a concrete structural difference from standard tree decomposition with no known analog in treewidth theory.

## 12. Next steps

1. **Formalize the factorization gap.** Prove that for the balanced partition constraint, the root pass rate drops to 0 for certain splits — making the factorization theorem fail. This would be a machine-checked proof that balanced partition resists tree decomposition at specific split points.

2. **Connect asymmetric flow to known models.** The left-first traversal with context accumulation resembles online algorithms (decisions made with partial information). Is there a formal correspondence between asymmetric tree verification and online computation? If so, competitive ratios from online algorithms might apply.

3. **Scale the density/coupling measurements.** The current experiments use 4-6 elements. Scaling to 8-12 would show whether the coupling measure (root pass rate) grows or shrinks with problem size, giving empirical evidence about the treewidth behavior.

4. **Test whether the asymmetry changes satisfiability.** The 18 disagreements show different VERIFICATION verdicts. But do they change the SEARCH outcome? Is there a set of elements where a satisfying tree exists under symmetric verification but NOT under asymmetric (or vice versa)? This would be the strongest evidence that the traversal order is computationally fundamental.
